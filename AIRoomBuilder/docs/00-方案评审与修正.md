# 方案评审与修正

对原始技术方案的逐条评审。结论先行：**主干路线正确，但选型偏重，且存在一处会直接卡死开发的坐标系断层。**

---

## 一、原方案做对的地方（保留）

| 决策 | 评价 |
| --- | --- |
| 不做真实 3D 重建，走「视觉理解 + 结构推理 + Web 渲染」 | ✅ 正确且关键。真实重建（MVS / NeRF / 3DGS）单人三周必然失控 |
| 用 `scene.json` 作为 AI 与渲染器之间的契约 | ✅ 全方案最有价值的一条。它把「AI 不稳定」和「渲染确定性」隔离开 |
| Three.js + glTF 做展示 | ✅ 免安装、跨平台、演示效果好 |
| 分阶段推进、给 AI 拆小任务 | ✅ 正确的协作方式 |

---

## 二、必须修正的问题

### ❌ P0：坐标系断层（最致命）

原方案第一阶段让视觉模型输出：

```json
{ "name": "sofa", "position": { "x": 0.2, "y": 0.6 } }
```

第二阶段却直接要用：

```json
{ "type": "sofa", "position": [1, 0, 2] }
```

**这两个坐标不是一个东西。** 前者是**图像平面归一化坐标**（照片里沙发在画面左下），后者是**房间俯视平面的米制坐标**。从前者推后者需要相机内参、相机位姿、逐像素深度——这正是你决定不做的「真实 3D 重建」。方案在这里悄悄跳过了最难的一步。

**修正方案：不要问模型「它在图片的哪里」，直接问「它在房间平面图的哪里」。**

多模态模型具备俯视布局的常识推理能力（它见过大量户型图）。让它直接输出：

```json
{
  "category": "sofa",
  "floor_uv": [0.22, 0.15],        // 俯视平面归一化坐标，非图像坐标
  "against_wall": "north",          // 靠墙关系，比坐标更可靠
  "facing": "into_room",
  "size_class": "L"
}
```

关键洞察：**`against_wall` 这类离散的拓扑关系，模型的准确率远高于连续数值坐标。** 所以让坐标只做粗定位，用拓扑关系在服务端做吸附矫正。这是整套方案能否落地的分水岭。

---

### ❌ P0：尺寸幻觉

让视觉模型输出「沙发长 2.3 米」，它会给你一个看似合理、实则随机的数。同一张图跑两次能差 40%。

**修正：模型只输出 `category` + `size_class(S/M/L)`，真实米制尺寸由服务端的家具尺寸先验表决定。**

沙发就是 2.0×0.9×0.8 m，双人床就是 1.5×2.0×0.5 m——这些是行业标准件，查表比问模型准得多，而且完全可复现。见 `backend/app/services/catalog.py`。

---

### ❌ P0：缺少布局后处理层

原方案是「AI 出坐标 → Three.js 摆放」，中间没有任何校验。实际结果一定是：沙发穿进墙里、茶几和沙发重叠、电视柜浮在房间中央。

**必须补一层 layout solver：**

1. 边界钳制（物体包围盒不得出房间）
2. 靠墙吸附（`against_wall` 指定的墙面对齐 + 朝向修正为面向房间内部）
3. 重叠消解（俯视矩形做迭代分离）
4. 依附关系（茶几吸附到沙发前方 0.4 m、床头柜吸附到床两侧）

**这一层对最终观感的提升，大于换更贵的视觉模型。** 见 `backend/app/services/scene_builder.py`。

---

### ⚠️ P1：技术栈过度工程

PostgreSQL + Redis + Celery + Docker + Nginx 对「单人 / 个人电脑 / 三周 Demo」是纯负担。你会把大量时间花在容器网络、Celery worker 不消费、Redis 连接池上，而不是花在效果上。

| 原选型 | 建议起步 | 何时升级 |
| --- | --- | --- |
| PostgreSQL | **SQLite** | 需要并发写 / 上线时（SQLAlchemy 下改一行 DSN） |
| Celery + Redis | **FastAPI BackgroundTasks** | 分析任务 > 30s 或需要多 worker |
| Docker + Nginx | **本地直跑** | 真要部署时再加，别提前 |
| Element Plus **+** Ant Design Vue | **只留 Element Plus** | 永远不要同时装两个 UI 库 |
| ECharts | **砍掉** | 真有统计看板需求时再加 |

省下来的时间投到「家具模型质量」和「布局合理性」上，演示效果的边际收益高一个数量级。

---

### ⚠️ P1：Depth Anything / SAM2 推迟

两者都要拉 GPU 依赖和数百 MB 权重，调通成本高，但对「看起来像不像那个房间」的贡献远低于预期——因为你最终渲染的是标准家具模型，不是重建的点云。

**房间尺寸用更笨但更有效的办法**：按房间类型给预设（客厅 5.0×4.0×2.8 m，卧室 3.6×3.6×2.8 m），前端给用户三个滑块随手调。用户调 5 秒钟，比深度估计准，还不用装 PyTorch。

深度估计放到 P2，作为「自动初始化尺寸」的锦上添花。

---

### ⚠️ P1：模型资产是真正的瓶颈（原方案完全没提）

`sofa.glb` / `table.glb` 从哪来？这是整个项目最容易翻车的地方——代码全写完了，场景里空空如也。

**两条硬要求：**

1. **必须有降级渲染**：找不到对应 glb 时，用参数化几何体按真实尺寸生成一个有基本造型的替身（不是灰盒子），并保持包围盒正确。这样任何分析结果都能出图。
2. **模型库要可控**：优先选风格统一的 CC0 套件，混搭不同来源的模型会让场景看起来很廉价。

推荐来源（均可商用 / CC0）：

- **Kenney Furniture Kit** — 风格统一、体积小、最适合做 Demo
- **Poly Haven** — 质量高，CC0
- **Sketchfab** CC0 筛选 — 补缺失品类

先只准备 12 个高频品类：沙发、茶几、电视柜、餐桌、餐椅、床、床头柜、衣柜、书桌、办公椅、书架、地毯。覆盖 80% 场景。

---

### ⚠️ P2：VLM 调用成本与可复现性

开发期你会对同一张图反复调试 Prompt。**必须做结果缓存**：`sha256(图片) + prompt版本` 作为 key，命中直接返回。否则一天能烧掉几十块，而且每次结果都不一样，根本没法调试布局算法。

骨架里已内置文件级缓存 + `mock` provider（无 API Key 也能跑通全流程）。

## 三、修正后的数据流

```
照片
 │
 ├─(1) VLM 视觉分析 ──→ analysis.json   { 房间类型, 物体category, 俯视uv, 靠墙关系, size_class }
 │                        ↑ 不含米制尺寸、不含图像坐标
 │
 ├─(2) 尺寸先验查表 ──→ 每个物体拿到真实 W×D×H
 │
 ├─(3) 布局求解器 ────→ 钳制 / 吸附 / 去重叠 / 朝向修正
 │
 ├─(4) 资产绑定 ──────→ 匹配 glb，缺失则标记为 primitive 降级
 │
 └─(5) scene.json ───→ Three.js 确定性渲染
```

第 2、3、4 步是纯确定性代码，**AI 的不确定性被限制在第 1 步**。这是整个架构的核心思想。

---

## 四、最终建议技术栈

```
前端   Vue 3 + TypeScript + Vite + Pinia + Element Plus + Three.js
后端   Python 3.10 + FastAPI + SQLAlchemy + SQLite
AI     Qwen-VL / GPT-4o / Gemini（适配层可切换，含 mock）
布局   自研 solver（尺寸先验 + 吸附 + 分离）
3D     Three.js + glTF，缺模型自动降级为参数化几何体
后续   PostgreSQL / Redis / Celery / Docker（有需要再上）
```
