## ⚡ 快速开始：启动前后端

> 想立刻看到效果，只看这一节就够了。环境准备与原理说明见后文。

需要同时开**两个**命令行窗口，一个跑后端、一个跑前端。

**第 1 步：启动后端**

```bash
cd backend
..\venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

启动后：

- 后端接口：`http://127.0.0.1:8000`
- 健康检查 `http://127.0.0.1:8000/api/health` 返回 `ok:true` 即成功
- 自动生成的 API 文档（建议常看）：`http://127.0.0.1:8000/docs`

> Linux / Mac 把 `..\venv\Scripts\python` 换成 `python` 或你的虚拟环境路径。

**第 2 步：启动前端**（另开一个窗口）

```bash
cd frontend
npm install      # 第一次需要，安装依赖
npm run dev
```

启动后打开 `http://localhost:5173/` 即可使用。

**第 3 步：连起来用**

前端跑在 `:5173`，后端跑在 `:8000`。前端代码里请求写的是相对路径 `/api/...`，由 Vite 开发服务器在后台自动转发到 `:8000`——所以你只管打开 `:5173` 操作即可。**没有视觉模型 Key 时会自动用内置样例数据，不联网也能跑通整条链路。**

> 需要换视觉模型、改数据库路径、或遇到端口占用等问题，见第 6 节「如何把项目跑起来」与第 10 节「排错小贴士」。

## 1. 先理解三件最基础的事

### 1.1 什么是「界面程序」和「服务端程序」

一个网页应用通常由两部分组成，可以类比成**餐厅**：

| 角色 | 在餐厅里 | 在 AI Room Builder 里 | 用什么写 |
| --- | --- | --- | --- |
| **界面程序（前端）** | 菜单、服务员、餐桌布置——你看得见、摸得着的部分 | 网页上你点的按钮、上传图片的框、三维房间画面 | Vue 3 + TypeScript |
| **服务端程序（后端）** | 后厨——你看不见，但真正干活、炒菜的地方 | 接收图片、调用 AI 模型识别家具、算出三维坐标、把结果存数据库 | Python + FastAPI |
| **浏览器** | 顾客 | 你用的 Chrome / Edge | — |
| **网络** | 你和服务员之间的对话 | 前端和后端之间来回传的数据 | HTTP 协议 |

一句话：**前端负责「好看、好点」；后端负责「算得对、存得住」**。

本项目的分工：

- 你（浏览器）打开网页 → 网页是**前端**。
- 你点「上传房间照片」→ 前端把照片发给**后端**。
- 后端偷偷调用大模型，识别出「这里有个沙发、那里有张桌子」，再算出每件家具放在房间什么位置 → 生成一份叫 `scene.json` 的数据。
- 后端把这份数据回传给前端。
- 前端用 Three.js 把这份数据画成你能旋转查看的三维房间。

### 1.2 前端和后端是怎么「说话」的

它们通过互联网上最常见的 **HTTP 协议** 对话，方式是「一问一答」：

1. 前端发出一个**请求（request）**：「我要上传这张图片」或者「给我第 5 张图的分析结果」。
2. 后端处理完后返回一个**响应（response）**：成功就带数据回来，失败就带错误原因。
3. 两边约定好用 **JSON** 这种统一格式来装数据（长得像 `{ "name": "沙发", "color": "#808080" }`）。

这种「前端问、后端答」的接口，在行业里叫 **API（应用程序接口）**。本项目的所有 API 都以 `/api` 开头。

### 1.3 一次完整流程（建议先读这一节，再读代码）

```
你(浏览器)
  │  ① 选照片，点上传
  ▼
前端 (Vue 网页, :5173)
  │  ② 发 POST /api/images/upload（照片二进制）
  ▼
Vite 开发代理 (把 /api 转发到 :8000)
  │
  ▼
后端 (FastAPI, :8000)
  │  ③ 存照片，后台调用视觉模型分析
  ▼
后端写库，分析完成
  │  ④ 前端轮询 GET /api/images/{id}/analysis 直到 status=done
  ▼
后端返回识别结果(JSON)
  │  ⑤ 前端发 POST /api/scenes/generate
  ▼
后端把识别结果 → scene.json（三维契约）
  │  ⑥ 返回 scene.json 给前端
  ▼
前端 Three.js 把 scene.json 画成三维房间
```

每一行的「谁、在哪个文件、做什么」，见第 7 节「关键代码示例位置索引」。

### 2.3 三维与 AI 专项

- **三维渲染**：完全由 Three.js 完成，入口是 `frontend/src/three/RoomRenderer.ts`。它**只读取** `scene.json`，不关心 AI 怎么算出来的——这是有意为之的解耦。
- **视觉模型（VLM）**：通过 OpenAI 兼容接口调用（本项目接的是 `ai.ibilieve.com` 网关的 `agnes-2.0-flash` 模型）。适配代码在 `backend/app/services/vision.py`。**没有 API Key 时会自动用 `mock` 内置样例数据**，保证不联网也能跑通整条链路。
- **颜色分析**：用 OpenCV + KMeans 聚类，对每张家具区域算出主色，写进 `scene.json`。代码在 `backend/app/services/color_service.py`。

### 4.1 各文件夹中每个文件的代码功能

下面按文件夹、按文件，逐一说明**每个文件里的代码是做什么的、关键函数叫什么**。这是给接手者最实用的一节——顺着这里去找源码即可。

#### 4.1.1 根目录

- **README.md**：项目总览（一句话定位、技术栈、快速开始）。新人第一眼先看它。
- **docs/**：所有协议与路线文档（见 4.1.6）。
- **models/**：26 个家具三维模型 `.glb`（见 4.1.4）。
- **tools/**：离线模型生成脚本（见 4.1.5）。
- **backend/ / frontend/**：前后端代码（见下）。

#### 4.1.2 backend/（服务端，Python）

- **backend/.env**：运行期配置（**不入库，含密钥**）。含 `VISION_PROVIDER`（mock / openai / dashscope / gemini）、`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL`、各厂商 Key、`DATABASE_URL`。要换模型或改数据库路径，只动这里。
- **backend/requirements.txt**：后端依赖的精确版本清单（FastAPI、OpenCV、NumPy、scikit-learn、SQLAlchemy、Pydantic、httpx、Pillow……）。新人装环境照它装。
- **backend/smoke_test.py**：**后端离线自检脚本**（不依赖 HTTP 服务）。`main()` 直接跑 `analyze_image` → `build_scene` 全链路，覆盖 `MOCK_SAMPLES` 每套样例，校验四条硬不变量（物体不出界 / 落地家具不重叠 / 靠墙家具背面贴墙 / 字段符合 schema），并把示例场景导出为 `backend/data/sample_scene_*.json`。改了布局或识别算法后先跑它：
  ```bash
  cd backend && ..\venv\Scripts\python smoke_test.py
  ```
- **backend/app/__init__.py**：Python 包标识（空文件），让 `backend/app` 能被 import。
- **backend/app/main.py**：FastAPI 总入口。
  - 定义 `app`（标题、版本、Swagger 描述、OpenAPI tags）。
  - `lifespan`：启动时 `init_db()` 建表。
  - 配置 CORS（允许 5173 前端跨域，是正式部署的安全网）。
  - 挂载两个静态目录：`/models`（家具 glb）、`/uploads`（上传图）。
  - `health()`：`GET /api/health` 返回服务可用性与当前生效的视觉模型。
- **backend/app/config.py**：**配置中心**。`Settings`（pydantic-settings）从 `.env` 读取所有配置；启动时自动建好 `data/`、`uploads/`、`vision_cache/`、`models/` 目录。关键函数：`resolved_provider()`——没配对应 Key 时自动回退 `mock`；`resolved_model()`——返回实际模型名。
- **backend/app/db.py**：**数据库引擎与会话**。`engine`：SQLAlchemy 引擎（SQLite，含 `check_same_thread` 处理）；`SessionLocal`：会话工厂；`Base`：ORM 基类（所有表模型继承它）；`get_db()`：每个请求用的会话生成器（用完关闭）；`init_db()`：建表（`Base.metadata.create_all`）。
- **backend/app/models.py**：**数据库表结构（ORM 模型）**。`Project`：项目表（id、name、created_at，一对多关联图片与场景）；`Image`：图片表（project_id、filename、path、宽高、status、error、analysis_result JSON 文本）；`Scene`：场景表（project_id、image_id、scene_json 文本、时间戳）。
- **backend/app/schemas.py**：**接口进出参的数据格式（Pydantic）**。请求：`ProjectCreate`、`RoomOverride`（手动覆盖房间尺寸）、`SceneCreate`（带 image_id + 可选 room）；响应：`ProjectOut`、`ImageOut`、`AnalysisOut`（含 status/analysis）、`SceneOut`、`SceneUpdate`。这些 model 决定 API 收到/返回什么字段，前后端共用同一套字段约定。
- **backend/app/api/__init__.py**：把三个路由（`projects`、`images`、`scenes`）汇总到 `/api` 前缀下，供 `main.py` 一次性 `include_router`。
- **backend/app/api/projects.py**：**项目 CRUD**。`create_project` / `list_projects` / `get_project` / `delete_project`（删除级联删图片与场景）。
- **backend/app/api/images.py**：**图片上传与分析接口**。`upload_image`（POST `/images/upload`）：校验格式/大小 → 用 Pillow 把长边缩到 ≤1600px → 存盘 → `BackgroundTasks` 后台跑 `_run_analysis` → 立即返回（前端轮询结果）；`_run_analysis`：后台任务，独立开 Session 调 `vision.analyze_image`，把结果写回 `Image` 行（status 在 pending→running→done/failed 间流转）；`list_images`、`get_analysis`（轮询用）、`reanalyze`（重跑分析）。
- **backend/app/api/scenes.py**：**场景生成与查询**。`generate_scene`（POST `/scenes/generate`）：取已完成图片的分析结果 → 调 `scene_builder.build_scene`（可传房间尺寸覆盖）→ 存库返回 scene.json；`list_scenes` / `get_scene` / `update_scene`（PUT，拖拽编辑后回存）；`get_catalog`（GET `/scenes/meta/catalog`）：返回受控品类与房型默认尺寸，给前端下拉框用。
- **backend/app/services/__init__.py**：包标识（空）。
- **backend/app/services/vision.py**：**视觉模型适配层（全项目最复杂之一）**。`analyze_image(path)`：统一入口，屏蔽各厂商差异；先查缓存（sha256(图)+prompt 版本+provider），未命中再调对应 provider；对真实模型再跑 OpenCV 颜色分析；写缓存。`_call_mock` / `_call_openai` / `_call_dashscope` / `_call_gemini`：四个 provider，统一走 `_post_json`（对 5xx / 超时 / 坏 JSON 自动重试，4xx 不重试）。`extract_json(text)`：从模型返回里抠出第一个完整 JSON（容错 ```json 包裹和前后废话）。`MOCK_SAMPLES`：两套内置样例（客厅/卧室），没 Key 时直接用，保证开箱即跑。`VisionError` / `EmptyResponseError`：异常类型（空回包按可重试瞬时故障处理）。
- **backend/app/services/color_service.py**：**OpenCV 真实颜色分析**。`analyze_color(image_path, bbox)`：读图 → bbox 取区域（自动识别像素/归一化/百分比）→ 转 HSV → 过滤低饱和/过暗/过亮噪声 → KMeans 聚类 → 优先选「有彩色且占比不低」的主簇（避免选中墙/地板背景色）→ 返回 `{name, name_cn, hex, ratio}`。`_bbox_to_slices`：bbox 单位识别与越界 clamp。`_dominant_color`：KMeans + 彩色优先逻辑。`_name_for_hsv`：按 HSV 给主色打可读中文色名。`enrich_objects_with_color`：批量给分析结果里的 objects 补 `color` 字段。
- **backend/app/services/scene_builder.py**：**识别结果 → scene.json 的确定性构建（项目核心）**。`build_scene(analysis, room_override)`：对外总入口，构建后剔除内部字段。`SceneBuilder` 类：`build()` 主流程——房间定尺（用户覆盖 > 模型估算 > 房型预设）→ 逐物体 `_make_object`（品类归一化、尺寸查表、朝向推导、贴墙吸附、高度、资产绑定、颜色）→ `_apply_attachments`（茶几贴沙发前 / 办公椅贴书桌前 / 床头柜贴床两侧）→ `_clamp_to_room`（边界钳制）→ `_resolve_overlaps`（俯视矩形迭代分离，靠墙家具只沿墙滑）→ `_build_openings`（门窗）。辅助：`snap_to_wall`、`_footprint`（旋转后占地互换）、`_forward`（正面向量）、`_push` / `_locked_axis`（重叠分离时尊重贴墙约束）。
- **backend/app/services/catalog.py**：**家具尺寸先验目录 + 受控词表**。`Prior` 数据类：每件家具的 S/M/L 尺寸、默认色、安装方式（落地/挂墙/吸顶）、是否贴墙、glb 文件名、依附关系。`CATALOG`：26 个品类的先验表（项目不让视觉模型输出米数，真实尺寸全在这里查）。`ALLOWED_CATEGORIES`：受控品类清单；`ALIASES`：中英文别名归一化（「沙发」→sofa 等）。函数：`normalize_category`（自由文本→受控词）、`get_prior` / `get_size` / `get_room_default`、`ROOM_DEFAULTS`（各房型默认尺寸）。
- **backend/app/services/prompts.py**：**发给视觉模型的提示词**。`SYSTEM_PROMPT`：定位为「俯视平面布局分析专家」，只输出 JSON。`build_user_prompt()`：定义 u/v 坐标系、输出字段要求（category 必须受控词表、size_class 只给 S/M/L、against_wall、rotation_hint、bbox、room 尺度估算）。`PROMPT_VERSION`：改 prompt 必须升版本号，否则命中旧缓存。`EDIT_SYSTEM_PROMPT`：自然语言改布局用的补丁格式约定（S8 用）。
- **backend/data/**：运行期自动生成（上传图片、视觉缓存、导出的示例场景），**不入库**；用 `.gitkeep` 占位。

## 5. 核心契约：scene.json（务必先读 `docs/01-scene协议.md`）

前后端之间**唯一**的硬约定就是 `scene.json`。可以理解为：

> **后端负责「想清楚房间里有什么、放在哪」；前端负责「照着画出来」。中间传递的纸条就是 scene.json。**

最精简的结构长这样（完整字段见 `docs/01-scene协议.md`）：

```jsonc
{
  "room": { "type": "living_room", "width": 5.0, "depth": 4.0, "height": 2.8 },
  "objects": [
    {
      "category": "sofa",
      "label": "三人布艺沙发",
      "size": { "w": 2.0, "d": 0.9, "h": 0.8 },
      "position": [-0.6, 0, -1.55],
      "rotation_y": 0,
      "material": { "color": "#8d9aaf", "name": "灰" }
    }
  ]
}
```

- `position` 是 `[x, y, z]`（米），原点在房间地面中心，Y 轴朝上。
- `rotation_y` 是绕 Y 轴旋转的角度（度）。
- `category` 必须是 `catalog.py` 里的受控词表之一，否则会降级成「未知」形状。

**这条契约前后端共用**：后端在 `scene_builder.py` 里生成它，前端在 `types/scene.ts` 里定义它的类型，渲染时在 `RoomRenderer.ts` 里消费它。

## 6. 如何把项目跑起来

需要同时开**两个**命令行窗口（一个跑后端，一个跑前端）。

### 6.1 启动后端（Windows）

```bash
cd backend
..\venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

启动后：

- 后端接口地址：`http://127.0.0.1:8000`
- **API 文档（自动生成，强烈建议常看）**：`http://127.0.0.1:8000/docs`
- 健康检查：`http://127.0.0.1:8000/api/health`

> `--reload` 表示改了后端代码会自动重启，方便调试。Linux/Mac 把 `..\venv\Scripts\python` 换成 `python` 或你的虚拟环境路径。

### 6.2 启动前端

```bash
cd frontend
npm run dev
```

启动后打开 `http://localhost:5173/` 即可使用。

### 6.3 它们是怎么连起来的（重点）

前端跑在 `:5173`，后端跑在 `:8000`，端口不一样。前端代码里请求写的是相对路径 `/api/...`（见 `frontend/src/api/index.ts` 的 `baseURL: '/api'`）。

靠的是 `frontend/vite.config.ts` 里配置的**开发代理**：Vite 在开发时会把 `/api`、`/models`、`/uploads` 开头的请求自动转发到 `http://127.0.0.1:8000`（后端）。所以：

- 浏览器只跟 `:5173` 说话；
- `:5173` 默默把 API 请求转给 `:8000`；
- 你写前端代码时**永远只写相对路径 `/api/...`**，不用关心后端真实地址。

这就是为什么后端 `main.py` 里还要配 CORS（跨域白名单）——它是正式部署时的安全网，开发期有代理基本用不到。

> 最直观的方式：后端跑起来后直接打开 `http://127.0.0.1:8000/docs`，每个接口都能在线试。

## 10. 排错小贴士（基础版）

| 现象 | 可能原因 | 怎么查 |
| --- | --- | --- |
| 网页打不开 / 一直转圈 | 前端没启动，或端口不是 5173 | 看 `npm run dev` 的输出里 `Local:` 地址 |
| 上传后报错 / 没反应 | 后端没启动，或 `:8000` 被占用 | 访问 `http://127.0.0.1:8000/api/health` 看是否返回 `ok:true` |
| 报 CORS / 跨域错误 | 前端直连了 `:8000` 而非走 `/api` 代理 | 确认 `api/index.ts` 里 `baseURL` 是 `/api`，且前端经 `:5173` 访问 |
| 三维房间是空的 / 全是方块 | 没识别到家具，或 glb 模型缺失走了替身几何体 | 看后端 `/api/images/{id}/analysis` 返回了什么；模型在 `models/` 下 |
| 颜色不对 | 物体 bbox 区域混入了背景 | 看 `color_service.py`，必要时调 bbox 或聚类阈值 |
| 改了后端代码不生效 | 没开 `--reload`，或旧进程占着端口 | 确认启动命令带 `--reload`；`netstat` 查 `:8000` |
| 数据库只读报错 | 当前环境把 `backend/data/app.db` 锁成只读 | 在 `backend/.env` 里用 `DATABASE_URL` 指到其他可写路径（见 `.env` 注释） |

## 11. 给基础读者的学习路线建议

按这个顺序读代码，理解成本最低：

1. **先跑起来**（第 6 节），用内置示例 / mock 模式点一遍流程，建立「整体感」。
2. 读 `docs/01-scene协议.md`，搞懂 scene.json 长什么样——这是前后端的「共同语言」。
3. 读 `frontend/src/api/index.ts`，看前端是怎么发请求的（最小可运行的 HTTP 示例）。
4. 读 `frontend/src/stores/workspace.ts` 的 `runPipeline()`，看清「上传→分析→生成」三步在代码里怎么串起来。
5. 读 `backend/app/api/images.py` 的 `upload_image`，看后端怎么接请求、存文件、起后台任务。
6. 读 `backend/app/services/scene_builder.py` 的 `build_scene`，看识别结果怎么变成 scene.json。
7. 最后读 `frontend/src/three/RoomRenderer.ts`，看 scene.json 怎么被画成三维房间——这是本项目最「硬核」也最有成就感的一块。

> 提示：每一个 `services/` 下的文件都带有详细的中文 docstring，读源码时先看文件顶部注释，通常能省掉一半时间。
